# 比較ワークシート

A案・B案を読み比べて、5つの論点それぞれについて自分のチームの立場を決めてください。
**「そう決めた理由」がいちばん大事な欄です。**

想定するチームは、実際の自分のチームでOK。一人で仕事をしている人は
「未来の自分＋AIとのチーム」や「外注パートナーと組むとき」を想定してください。

---

## 論点1：命名の厳密さ

- A案：BEMを厳密に適用（ネスト表現禁止・`is-`/`js-` の使い分けまで規定）
- B案：ゆるやかなBEM（迷ったら短い名前でよい・ファイル内で統一されていればよい）

**うちのチームは**： [●] A寄り　[ ] B寄り　[ ] 独自

**そう決めた理由**：
担当者ごとの独自な命名を減らし、記述ルールを統一することで、後から見ても構造や役割が分かりやすく、可読性・保守性を高められるため。

---

## 論点2：ファイル分割の粒度とレイヤー構成

- A案：レイヤー6層固定・1コンポーネント1ファイル・200行で分割検討
- B案：4層を基本に必要なら追加・500行までは1ファイルでよい

**うちのチームは**： [ ] A寄り　[●] B寄り　[ ] 独自

**そう決めた理由**：
最初から細かく分割しすぎると管理が煩雑になるため、基本構成はシンプルにし、ページ数や記述量の増加に応じて必要な単位で分割することで、可読性・保守性を維持しやすくするため。
---

## 論点3：トークン化の基準

- A案：値の直書き全面禁止・Figmaと完全一致・変更は双方レビュー必須
- B案：2回以上使う値からトークン化・名前のずれは対応表で吸収

**うちのチームは**： [ ] A寄り　[●] B寄り　[ ] 独自

**そう決めた理由**：
一度しか使わない値まで先回りしてトークン化すると、トークン数が増えすぎて管理が煩雑になるため。複数箇所で使用する値から必要に応じてトークン化し、Figmaとの命名差異は対応表で管理することで、過度に厳格にせず運用しやすい状態を保てるから。
---

## 論点4：禁止事項の強さ

- A案：`!important` 例外なし禁止・ID装飾禁止・インラインスタイル禁止
- B案：`!important` はutilitiesのみ許可・「禁止」より「推奨」・理由コメントで例外許容

**うちのチームは**： [●] A寄り　[ ] B寄り　[ ] 独自

**そう決めた理由**：
!important やIDセレクタ、インラインスタイルを使用すると、詳細度が高くなりすぎて後からスタイルを上書きしにくくなり、CSSの管理が複雑になるため。例外を設けず禁止事項を明確にすることで、記述方法を統一し、保守性の高い状態を維持できると考えたため。
---

## 論点5：ツールでどこまで強制するか

- A案：Stylelint + Prettier 必須、CIでマージブロック
- B案：Prettierのみ必須、Stylelintは提案ベース

**うちのチームは**： [ ] A寄り　[●] B寄り　[ ] 独自

**そう決めた理由**：
記述ルールは明確にして統一したいが、すべてをツールやCIで強制すると設定や運用の負担が大きくなるため。Prettierによるフォーマットの統一は必須とし、その他のルールについてはコードレビューなどで確認する運用が適していると考えたため。
---

## メモ：いちばん迷った論点
Stylelintを必須にするかどうかの部分。必須にした方が記述は統一されると思うが、あまり細かくルールを決めすぎると、実装の自由度が下がったり、例外対応がしづらくなったりする可能性があるため迷った。
